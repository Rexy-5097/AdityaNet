# SuryaNet: Physics-Informed Solar Flare Forecasting and Space Weather Intelligence Platform

SuryaNet is an operational AI platform designed to forecast solar flares before they occur using solar observations from India's first solar mission, **Aditya-L1**. By combining observations from two key instruments onboard Aditya-L1—**SoLEXS** (Solar Low Energy X-ray Spectrometer) and **HEL1OS** (High Energy L1 Orbiting X-ray Spectrometer)—SuryaNet serves as a space-weather operations center for satellite operators.

---

## Technical Stack & Architecture

- **FastAPI**: Modern, async-first web framework for high-performance API endpoints.
- **SQLModel / TimescaleDB**: PostgreSQL-based time-series database optimized for high-volume solar flux telemetry.
- **Redis**: High-performance caching and connection broker.
- **Python 3.11+ / PyYAML / Rich / SQLAlchemy**: Standard scientific stack.

## 1. Space Weather Data Management Platform

The SuryaNet Data Management Platform completely replaces legacy bash/wget scripts with a professional, modular, and version-controlled data ingestion pipeline. It enforces a complete scientific chain of custody, data quality validation, metadata indexing, and an extensible payload plugin architecture.

## 2. Platform Installation & Setup

All scripts are optimized for local execution on macOS (Apple Silicon M4) and Linux.

### Prerequisites
- Python 3.11+
- Virtual environment with scientific libraries installed (`astropy`, `numpy`, `pandas` are used by the Data Quality module).

### Installation
1. Setup virtual environment:
   ```bash
   python3 -m venv venv
   source venv/bin/activate
   ```
2. Install dependencies:
   ```bash
   pip install -r requirements.txt
   ```
   *Allowed packages: `requests`, `tqdm`, `pyyaml`, `rich`, `sqlalchemy` along with core data packages `numpy`, `pandas`, `astropy` for data validation.*

## 3. Configuration & Usage

### Step 1: Configuration (`config.yaml`)
Configure your parameters in `data_pipeline/config.yaml`. Note that the manifest database, inventory, checksums, and reports automatically resolve relative to the `current_dataset_version` to support isolated, reproducible experiments.

```yaml
cookie: "FGTServer=03DE1918...; JSESSIONID=..."
base_url: "https://pradan1.issdc.gov.in"
download_directory: "data_pipeline/downloads"
workers: 4
retry_count: 5
timeout: 30
verify_zip: true
generate_checksum: true
parallel_downloads: true
current_dataset_version: "dataset_v1"
```

### Step 2: Ingesting PRADAN Scripts
To import a new batch of URLs and session cookies from a legacy PRADAN downloader script:
```bash
python3 migrate_from_pradan.py --script legacy/pradan_downloader.sh --version dataset_v1
```
This script automatically:
- Extracts cookies and the base URL, updating `config.yaml`.
- Parses download paths and inserts them into the manifest database with a status of `Queued`.

### Step 3: Running Ingestion & Downloads
To execute the parallel downloader:
```bash
python3 data_pipeline/download_manager.py --version dataset_v1
```
This runs the orchestrator:
1. Queries the manifest database for `Queued` or `Failed` downloads.
2. Streams downloads in parallel using range-based chunk requests (supporting resuming).
3. Detects duplicate files via SHA256 hashes before moving files to the archive.
4. Quarantines corrupted files to `downloads/corrupted/`.
5. Uses payload plugins to verify ZIP/FITS integrity and index metadata.
6. Generates JSON/CSV inventories and a `download_report.md` coverage report.

## 4. Manifest Database Schemas

### Downloads Table
Tracks the download registry and provenance:
- `id` (INTEGER, Primary Key)
- `source_url` (TEXT, unique)
- `filename`, `payload`, `date`, `size`
- `checksum` (SHA256), `zip_crc` (CRC32 hex)
- `status` (e.g. `Queued`, `Downloading`, `Downloaded`, `Verified`, `Failed`)
- `download_time` (seconds), `download_timestamp` (RFC 3339 format)
- `pradan_query_params` (PRADAN parameters)
- `http_headers` (JSON-encoded response headers)
- `original_filename` & `local_filename`
- `path` (final path inside raw directory)
- `remarks` (ingestion/quality warnings)

### FITS Metadata Table
Tracks telemetry characteristics for fast querying:
- `id` (INTEGER, Primary Key)
- `download_id` (ForeignKey referencing downloads)
- `instrument`, `observation_date`
- `cadence` (temporal resolution)
- `num_rows` (number of rows in the FITS table)
- `start_time` & `end_time`
- `energy_channels` (JSON channel listing)
- `missing_percentage` (NaNs/corrupted rows ratio)

## 5. Resumption, Recovery, & Future Extensions

### Resumption Logic
- If interrupted, the download manager queries the manifest on restart and resumes only files marked `Queued` or `Failed`.
- It uses the HTTP `Range` header (if supported by PRADAN) to resume downloads from the exact byte where they stopped, appending to the existing `.part` file.
- SQLite is configured in WAL (Write-Ahead Logging) mode and uses a Python thread lock to protect concurrent database writes.

### Extensible Payload Plugins
To support future instruments (e.g. SDO, Hinode, Solar Orbiter) without code changes:
1. Create a new subclass of `BasePayloadPlugin` in `data_pipeline/plugins/`.
2. Implement the `match_url`, `verify`, `check_quality`, and `extract_metadata` methods.
3. The platform dynamically discovers and registers the plugin at runtime.
