# Sprint 22 — Bottleneck Analysis

**Conclusion:** Twelve bottlenecks block operator-grade performance. The critical path runs through the decision layer, not the model: the deployed alert thresholds are test-set-leaked (B1) *and* operationally useless (B2, 3.97% recall), and the already-computed fix was never deployed (B3). Until the decision layer is honest, improving the model (B4–B6) cannot be measured credibly, and the flagship multi-instrument claim (B5) is blocked on data no engineering can create. Every bottleneck below is traceable to a file; nothing speculative is included.

---

## B1 — Production alert thresholds were selected on the test set (CRITICAL, scientific validity)

The deployed `artifacts/operator_thresholds.json` (yellow=0.46, red=0.88, plus all three uncertainty-suppression tiers and both confidence-level cutoffs) was generated by `scripts/optimize_operational_policy.py`, whose docstring states: *"Sweeps calibrated probability thresholds on the saved test-set probabilities"* and whose inputs are `artifacts/calibration/probs.npy` / `labels.npy` — the 1,806,313-row test predictions (row count matches the test set in `artifacts/evaluation_audit_report.json`). Production `app/services/ml/inference.py` loads exactly this file. Consequently:

- Every test-set operator metric — trust score 0.524, 91.1% precision (`artifacts/operator_readiness_report.json`), TSS bootstrap CI [0.369, 0.393] "at operator thresholds" (`artifacts/bootstrap_metrics.json`) — evaluates thresholds on the same data used to select them. All are optimistically biased by construction.
- This is a publication-fatal flaw and an operator-trust-fatal flaw: the one number an operator relies on (the alert boundary) was fit to the exam answers.

Note the calibrator itself is clean — `scripts/calibrate_model.py` fits on validation (lines 191–202). The leak is confined to the threshold/policy layer.

## B2 — Deployed policy misses 96% of flares (CRITICAL, operational utility)

At the deployed thresholds + uncertainty suppression + RED confirmation, episode-level recall is 3.97% with TSS 0.039 (`artifacts/operator_readiness_report.json`: recall_pct 3.97, tss 0.039, criteria_passed 3/5). Independent corroboration: `artifacts/model_failure_evidence_report.md` found the 0.95 red tier yielded 0% recall in its analysis window. A forecast system that misses 24 of 25 flares provides negative operational value (operators learn to ignore it). And per B1, even these numbers are the *optimistic* version.

## B3 — The validated fix exists but was never deployed (HIGH, engineering discipline)

Sprint 5.6 built `scripts/refine_thresholds.py` specifically to redo threshold selection validation-only (lines 63–68 list the test files explicitly NOT loaded; output records `"test_data_used": false`). It produced `artifacts/operator_thresholds_validation_only.json` (yellow=0.14, red=0.95). `app/services/ml/inference.py` still loads the leaked file. Three threshold files now coexist (`artifacts/calibration/calibration_report.json` → 0.09/0.19; validation-only → 0.14/0.95; deployed → 0.46/0.88) with no versioning or provenance metadata in the deployed one.

## B4 — SC24→SC25 distribution shift (HIGH, fundamental)

Training positive rate 0.62% (SC24) vs test 23.2% (SC25 maximum) — `artifacts/research_dataset_report.json` (SC24: 109 M + 4 X flares; SC25: 1,945 M + 105 X). The model, calibrator, and any validation-derived thresholds are all conditioned on a quieter sun than the one being forecast. The validation split (2020–2022, 4.07% positive — `artifacts/research/validation.parquet`) sits between the two regimes, partially mitigating threshold transfer but not eliminating it.

## B5 — Aditya-L1 incremental value unproven (HIGH, blocks the flagship claim)

- Ablation: GOES-only TSS 0.405 vs full V3 0.413 — a 0.008 gap (`scientific_validation_report.md` §6).
- Conditional mutual information of SoLEXS/HEL1OS features given GOES history: 0.0 for all features (`artifacts/aditya_l1/incremental_information_audit.json`, classification "Class C").
- The only jointly-aligned GOES+Aditya-L1 evaluation corpus is 4 days with zero positive events (`artifacts/aditya_l1/overlap_dataset.parquet`, target positive rate 0.0000; `artifacts/aditya_l1/overlap_corpus_statistics.json`).

No engineering effort can conjure joint flare events; this bottleneck is **data-blocked** until more overlap era containing M/X flares is ingested from PRADAN archives (raw SoLEXS/HEL1OS files span Oct 2023 → Jun 2026 — `data/aditya_l1/processed/` — so the aligned corpus can likely be *extended backward* from existing raw data; the current 4-day window appears to be a build choice, not a data ceiling).

## B6 — Characterized failure modes untreated (MEDIUM, model quality)

`artifacts/model_failure_evidence_report.md`: false negatives are "stealth flares" from quiet backgrounds (mean 3,489 min since last flare) with near-uniform attention entropy (≈1.0); false positives cluster in post-flare decay (mean 441 min after a flare). Both modes are consistent with the model over-relying on history features (`artifacts/information_gap_report.json`: removing history → TSS 0.0). No mitigation has been attempted.

## B7 — model_v3.py defaults incompatible with trained checkpoint (MEDIUM, blocks V3 work)

`app/services/ml/model_v3.py` defaults: `n_features_solexs=25, n_features_hel1os=10`. Trained checkpoint shapes: `patch_embed_solexs.projection.weight [160, 288]` = 18×16; `patch_embed_hel1os.projection.weight [160, 64]` = 4×16 (`artifacts/sprint14c/checkpoints/model_seed_42_stage2_best.pt`; manifest `artifacts/feature_columns_v3.json`). Any naive V3 load fails.

## B8 — Temperature scaling produces TSS=0.000 (LOW, contained)

At fitted T=1.4168, temperature-scaled V3 test TSS is exactly 0.000 while isotonic achieves 0.384 (`scientific_validation_report.md` §2; `artifacts/sprint14c/test_results_model_D_seed_42.json`). Contained because isotonic is the selected method, but unexplained behavior in a calibration component erodes trust in the calibration stack.

## B9 — Window-level evaluation on stride-1 autocorrelated samples (MEDIUM, statistical rigor)

All headline metrics are computed over sliding windows at 1-minute stride (`app/services/ml/dataset.py`, `dataset_v3.py`: n_samples = len(labels) − seq_len), so adjacent samples share 359/360 of their input. Bootstrap CIs (`app/services/ml/metrics.py::paired_bootstrap_test`, n=1000) resample windows i.i.d., understating variance. Episode-level evaluation exists only once, in Sprint 5.5 (`artifacts/operator_readiness_report.json`), and is not part of the standard evaluation suite.

## B10 — No test suite, no auth, no ingestion scheduler, no app Dockerfile, no git (HIGH, engineering)

Verified absences: no pytest/unittest files, no auth middleware, no scheduler, no Dockerfile, no `.git` (absence documented in `PROJECT_STATUS.md`; git absence independently confirmed in `scientific_validation_report.md` §7: `"git_commit": "none"`). These block production but are not scientific bottlenecks.

## B11 — Cross-platform non-determinism (LOW, reproducibility)

Fresh MPS inference deviates from saved predictions by up to 9.76e-4, failing the 1e-6 reproduction tolerance (`scientific_validation_report.md` §2–3). Deterministic within-platform (SHA256-identical across 3 runs). Consequence: archived `.npz` predictions are the canonical record; hardware must be pinned for certification.

## B12 — Self-reported sprint statuses are unreliable (MEDIUM, process)

`artifacts/sprint20b/sprint20b_summary.json` reports `"validation_verdict": "PASS"`; the independent audit `validation_report_20b.md` concludes **FAIL** (parameter miscounts of +20,160/+5,760 buffer elements; `scripts/train_baseline.py` omitted from inventory). Same pattern as B1/B3: fixes get computed, reports get written, deployment/correction doesn't happen. Any Sprint 22 output must carry machine-checkable provenance.
